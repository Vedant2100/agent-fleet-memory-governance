## Actual demonstrated contribution

The study operationalizes a source-only decision to admit earlier task descriptions to a shared pool and a later, task-conditioned decision to expose admitted descriptions to a coding worker, then tests these choices on frozen related coding tasks. In the seven fully graded targets, it shows meaningful changes to exposed memory but no improvement in complete task resolution; the strongest apparent partial-test advantage occurs under Jev Write and coexists with regressions and run variability. These are development observations about an experimental intervention, not a validated method for improving a fleet of coding agents.

## Language and terminology edits (mandatory for writer round 1)

These are suggested phrasings, **not** a substitute for resolving substantive findings:

- Title: 'From Local Experience to Shared Knowledge in Coding-Agent Fleets' -> 'When Should Coding Agents Reuse Earlier Task Records? A Controlled Pilot Study' (or another equally precise, plain title).
- Abstract: 'A lightweight controller admits 123 cards, and its target-time filter exposes only one of 15 eligible retrieved cards' -> 'The controller stores 123 of 211 task records, but shows only one of 15 selected records to subsequent workers.' Clarify that selection/retrieval precedes filtering; do not change counts.
- Introduction: 'A shared memory service therefore poses two different decisions' -> 'A shared store raises two questions: which past records to keep, and which to show an agent working on a new issue.'
- Discussion: 'The intervention is mechanically meaningful' -> 'The two filters changed which records the worker received.' This is a measurable observation, not an evaluative adjective.
- Threats: 'source cards are task-derived proxies' -> 'These records summarize prior issues; they are not examples of what an earlier agent learned while solving them.'
- Replace 'Oracle ceiling' with 'known-related-memory condition'; 'governance' with 'record selection' when no access/verification/lifecycle policy was tested; and 'fleet' with 'separate coding-agent runs' when describing measured behavior. Keep words such as agent, memory, benchmark and retrieval where scientifically warranted.
- Abstract should lead with the question and setup, report the decisive full-resolution and regression findings, and end with the scope limitation. Avoid rhetorical claims of novelty, methods jargon before definition, excessive parenthetical abbreviations or a result list that looks like log output. Keep LaTeX headings conventional and restrained.

## Novelty assessment

**Closest overlap.** SWE-ContextBench already builds related coding-task histories and measures different ways to select and reuse context. Jev-Mem already operates a lightweight System-One memory controller over memory construction and retrieval; that functionality is prior work and this pilot's binary API decisions should not be presented as a new Jev-Mem mechanism. MemGuard already addresses memory admission, reliability and persistent verifier-derived metadata, while ReasoningBank stores distilled lessons from successful/failed agent interactions. ChainSWE measures linked coding repairs with persistent repository state; this pilot instead resets target sessions.

**Remaining potential distinction.** A source-only global admission policy combined with separate target-conditioned exposure, evaluated under frozen same-repo histories while holding retrieval and worker fixed, is a narrow experimental contrast. It might support a controlled AAMAS study if implemented controls, reproducibility and an informative result are established. Presently only exposure differences, partial-test anomalies and strong negative/repeatability findings are demonstrated; there is no confirmed advantage over size-matched Random, Share-All or No Memory. More defensible framing may be a failure analysis of memory-selection benchmarks, not a successful fleet-governance method.
